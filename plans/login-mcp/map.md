# Map: login-mcp

## Destination

sky-brain has real sign-in: Better Auth 1.7.15 runs inside the Express app on the existing Drizzle
database, people sign in with Google (only `ALLOWED_EMAILS` and the bootstrap owner get in;
everyone else sees "No access"), each person gets their own workspace at first sign-in and pending
invites are accepted at every sign-in, `/api/v1` knows the caller from the session cookie, and sky-brain is its
own OAuth 2.1 authorization server with CIMD, PKCE and JWT access tokens bound to
`<PUBLIC_URL>/mcp`. `/mcp` serves MCP over streamable HTTP with one tool, `whoami`, acting for the
person the token names and listing every workspace they belong to. `render.yaml` carries the auth settings, `docs/CONNECT.md` says how to
connect claude.ai, the phone app and Claude Code, and the Render plan is decided.

**The bar.** `pnpm install --frozen-lockfile && pnpm lint && pnpm typecheck && pnpm test` exits 0,
and `pnpm --filter @sky-brain/server exec vitest run src/mcp/claude-flow.test.ts --reporter=verbose`
prints `claude.ai flow: CIMD client signs in with Google and whoami returns the email` among the
tests that cover the 401 challenge, the discovery documents, PKCE to
`https://claude.ai/api/mcp/auth_callback` and a loopback redirect on any port. Then, after deploy
with shammai's Google client, claude.ai's `whoami` returns shammai's email (manual, recorded in
`docs/CONNECT.md` as the line `- claude.ai whoami: returned <email> on <YYYY-MM-DD>`). The
acceptance ticket (07) runs both.

- plan — Spike (scratch folder, not committed): Express 5.3.0 + better-auth 1.7.15 (drizzle
  adapter on PGlite 0.5.14, tables generated by `auth generate --adapter drizzle --dialect
  postgresql` and migrated by drizzle-kit 0.31.11) + jwt + mcp + cimd with a fake CIMD fetch and
  a stubbed Google token endpoint ran the whole flow: `POST /mcp` 401 with
  `Bearer resource_metadata="<origin>/.well-known/oauth-protected-resource/mcp"`; both
  protected-resource paths and `/.well-known/oauth-authorization-server/api/auth` answered with
  `resource` `<origin>/mcp`, issuer `<origin>/api/auth`, `S256`, `none`,
  `client_id_metadata_document_supported: true` (the root `/.well-known/oauth-authorization-server`
  is 404); authorize → `/sign-in?<signed query>` → `sign-in/social` with `oauth_query` → Google
  callback → `/consent?...` → `oauth2/consent` → `https://claude.ai/api/mcp/auth_callback?code=`
  → token (form-urlencoded, PKCE) → JWT with `aud` `[<origin>/mcp, <origin>/api/auth/oauth2/userinfo]`,
  `iss` `<origin>/api/auth`, `sub` the user id, `azp` the client id; a reused code gave
  `invalid_grant`; `http://localhost:53682/callback` and `http://127.0.0.1:3118/callback` were
  accepted for a client registered with `http://localhost/callback` and `http://127.0.0.1/callback`;
  `https://evil.example/cb` ended at `/api/auth/error?error=invalid_redirect`; a tampered token and
  `?access_token=` got 401; `whoami` through `createMcpHandler` (2025-06-18 `initialize`, SSE body)
  returned the email read by `sub`.
- plan — Spike: `databaseHooks.user.create.before` returning `false` for an uninvited email made
  the Google callback redirect to `<errorCallbackURL>?error=unable_to_create_user` with no user row
  and no session cookie. (Round 3: the plan now refuses in `user.validateUserInfo` instead, which
  also runs on later sign-ins; see the round 3 spike line.)
- plan — Spike quirks a builder needs: Node's `fetch` sends `sec-fetch-mode: cors`, so Better Auth
  answers it with `200 {"redirect": true, "url"}` instead of a 302 (a browser navigation gets the
  302); the Google callback answered 302 with `Location: /` but a JSON body whose `url` was the
  consent page, so follow the body's `url` first. A state-changing `/api/auth/*` request without an
  `Origin` header is 403 `MISSING_OR_NULL_ORIGIN`. Better Auth logs "could not seed `resources` at
  startup" with the memory adapter only.
- plan — Better Auth's default ids are 32 characters of `a-z A-Z 0-9`
  (`@better-auth/core/dist/utils/id.mjs`, `generateId`), so user ids fit `UserIdSchema`
  `^[A-Za-z0-9_-]{1,64}$` (the brief's assumption holds).
- plan — Google provider 1.7.15: the callback swaps the code at `https://oauth2.googleapis.com/token`
  through the global `fetch` and reads the profile by decoding (not verifying) the returned
  `id_token`; options `clientId`, `clientSecret`, `prompt`, `hd`; callback path
  `/api/auth/callback/google`, so the Google client needs
  `<PUBLIC_URL>/api/auth/callback/google`. docs: https://better-auth.com/docs/authentication/google
- plan — CIMD: the client id is an HTTPS URL; the document must carry `client_id` equal to that
  URL, `client_name` and `redirect_uris`; DCR is deprecated in favour of CIMD. The plugin's
  `fetchClientMetadataResource` must resolve DNS once, refuse special-use addresses and refuse
  redirects (the `/node` export does). docs:
  https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration
- plan — `createMcpHandler` defaults to `legacy: "stateless"` (serves 2025-era clients per request;
  GET and DELETE answer 405); `"reject"` serves only 2026-07-28. It performs no token check; the
  verified identity is passed as `fetch(request, {authInfo})` and reaches the factory as
  `ctx.authInfo`. (Read from `@modelcontextprotocol/server` 2.4.0 `createMcpHandler-*.d.mts`.)
- plan — The jwt plugin also serves `GET /api/auth/token`, a session JWT with another audience;
  `/mcp` must refuse it (ticket 05 tests it). Probe (round 2): with a session cookie it answered
  200 `{"token": "eyJ..."}`.
- plan — Option names at 1.7.15 (read from the installed `.d.mts`; the probe ran them):
  `mcp()` takes `OAuthOptions` plus `resource` (required; HTTPS, or HTTP on loopback only) and
  `refreshTokenReuseInterval` (default **30** seconds for MCP clients, "set to `0` to disable");
  `OAuthOptions` has `loginPage` (required), `consentPage` and `scopes` (default `["openid",
  "profile", "email", "offline_access"]`). Source: `@better-auth/mcp/dist/index.d.mts`,
  `@better-auth/oauth-provider/dist/oauth-m0aNFIHP.d.mts`; docs: https://better-auth.com/docs/plugins/mcp
- plan — `requireMcpAuth(auth, handler, opts?)` "verifies the bearer access token against the
  authorization server's JWKS (checking signature, issuer, audience, and expiry)" and answers
  others with a JSON-RPC 401 and the RFC 9728 `WWW-Authenticate` header; `opts` are `resource`,
  `issuer`, `jwksUrl`, `challengeScopes`, `requiredScopes`, `isScopeSatisfied`, `dpop`. It does
  **not** check `azp`: our `actorFromMcpClaims` must (ticket 05). The spike's 401 body without a
  header was `"missing authorization header"`, and `?access_token=` got 401. Source:
  `@better-auth/mcp/dist/index.d.mts` (`RequireMcpAuthOptions`, its doc comment).
- plan — `auth.api.signJWT({ body: { payload } })` (jwt plugin, server-only endpoint) returns
  `{ token }` signed with the server's JWKS key; probe: a token it signed with `aud`
  `<origin>/api/auth` got 401 on `/mcp`. Source: `better-auth/dist/plugins/jwt/index.d.mts`.
- plan — Spike (round 3, `scratchpad/spike-r3/hooks.mjs` on better-auth 1.7.15, memory adapter,
  Google stubbed): `user.validateUserInfo({ user, source })` ran as `create-user` on the first

  `databaseHooks.session.create.after` ran on every sign-in (three sign-ins, three calls), and on

  just before `create-user`, `link-account`, and (for OAuth) `sign-in` ... On `sign-in` the hook
  receives the *fresh* provider email and profile"; "return `{ error }` to reject. Browser flows
  redirect to the configured error URL". Source: `@better-auth/core/dist/types/init-options.d.mts`

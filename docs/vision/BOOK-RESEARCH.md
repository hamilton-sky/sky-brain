# Ship the book's text, not its machinery

Sky-brain should not build the brain book as designed now. It should build a small slice of it, and only after the two-week memory-loop measurement ends. The evidence says that at about 18 tools a frontier model's problem is rarely the number of tools. Its problem is method: which of two similar tools to use, in what order, and what goes wrong. Better tool descriptions and worked examples are the best-proven fix for that, with gains such as 72% to 90% on complex parameters ([Anthropic](https://anthropic.com/engineering/advanced-tool-use)). Progressive disclosure has a strong record, but only at scale. Anthropic itself says tool search is "less beneficial" below about 10 tools ([Anthropic](https://anthropic.com/engineering/advanced-tool-use)), and GitHub dropped its own discovery meta-tools from the defaults ([GitHub](https://github.com/github/github-mcp-server/discussions/1182)). Across clients, only tools and tool descriptions reliably reach the model. Server instructions are confirmed in Claude Code but undocumented in claude.ai. Prompts are user-invoked everywhere, and resources are model-readable only in Claude Code. The riskiest part of the design is the part that grows: model-proposed pages are model-written memory that later models read as instructions. That is the exact loop behind the SpAIware and persistent-memory-poisoning attacks. Recommended order: build the benchmark now, offline. After the measurement window, ship code-generated "use when / pitfalls" text in tool descriptions, a short server-instructions block, and one read-only `book` tool, and keep them only if the benchmark shows a gain. Defer `book_search`, person pages, model-proposed pages, the usage-suggestion engine, compact mode, resources and prompts, each behind a named trigger.

## At 18 tools, the evidence points to method, not overload

The strongest results on tool count come from settings far larger than sky-brain. In RAG-MCP's stress test, selection held above 90% while the target tool sat in the first ~30 positions, and failures dominated only beyond ~100 tools ([RAG-MCP](https://arxiv.org/html/2505.03275v1)). On LiveMCPBench (527 tools), **retrieval errors account for nearly half of all failures** ([LiveMCPBench](https://arxiv.org/html/2508.01780v2)). Small models are the exception that bites earlier. In "Less is More", an 8B model failed a query with 46 tools and succeeded with 19, and offering a subset of tools raised Llama3.1-8b's success by 44% on BFCL ([Less is More](https://arxiv.org/html/2411.15399v1)). Frontier models, by contrast, keep **99–100% valid tool names and schema compliance even with 100+ distractor tools**. Their failures sit in planning, dependency awareness and task completion ([MCP-Bench](https://arxiv.org/pdf/2508.20453)).

Vendors draw their line right where sky-brain sits. Anthropic recommends tool search at 10+ tools or more than 10K tokens of definitions ([Anthropic](https://anthropic.com/engineering/advanced-tool-use)). OpenAI says to aim for "fewer than 20 functions available at the start of a turn" and to "combine functions that are always called in sequence" ([OpenAI](https://developers.openai.com/api/docs/guides/function-calling/index.html)). Sky-brain alone is not overloaded. It becomes part of an overloaded context when a person connects several servers. The clients that suffer most from that, such as Claude Code, VS Code and Cursor, now defer tool details on their own (see the client section below).

Documentation quality, on the other hand, moves results a lot. Anthropic calls detailed descriptions "by far the most important factor in tool performance" and asks for at least 3–4 sentences per tool, covering when to use it and when not ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/implement-tool-use)). In research settings, rewriting tool docs into concise, structured instructions raised GPT-4's ToolBench success from **46 to 70** ([EasyTool](https://arxiv.org/pdf/2401.06201v2)). Self-refined docs lifted GPT-4o on RestBench-Spotify from **28% to 70%** ([DRAFT](https://arxiv.org/html/2410.08197v2)). MCP-Universe names the "unknown-tools challenge", agents not knowing how to use a server precisely, as a key failure cause ([MCP-Universe](https://arxiv.org/abs/2508.14704)). That is precisely the gap BOOK.md describes: `claim_task` already returns a context packet, an observation needs `refs`, a model must never claim an approval.

Two caveats temper this. The large gains come from weak baselines (poor docs, older or small models). For a frontier model on a reasonably described 18-tool server, expect single-digit to low-double-digit gains, concentrated in multi-step and look-alike cases. That is an estimate, and no study measures it directly. And examples are not free: OpenAI warns that "adding examples may hurt performance for reasoning models" ([OpenAI](https://developers.openai.com/api/docs/guides/function-calling)). Nobody has published an A/B test of a separate usage guide against good descriptions alone. Sky-brain would have to run that test itself.

## Index-first works when the index is always in view, and meta-tools often go unused

Every successful prior system shares one shape: a short index that is always visible, bodies loaded on demand, and descriptive one-line entries that act as the trigger. The successes and failures are worth comparing side by side.

| Prior art | What it does | Result | Lesson for the book |
| --- | --- | --- | --- |
| Agent Skills | Name and description always in the system prompt; SKILL.md read when relevant; sub-files later | No published accuracy numbers; discovery depends entirely on the description line ([Anthropic](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)) | The table-of-contents wording matters as much as the chapters |
| Skills over MCP (SEP-2640, Final) | Skills as `skill://` resources plus `skills/list` and `skills/get`; hosts must load lazily | Standard transport for exactly this pattern; client uptake unclear, ChatGPT "Partial" ([SEP-2640](https://modelcontextprotocol.io/seps/2640-skills-extension), [matrix](https://modelcontextprotocol.io/extensions/client-matrix.md)) | Watch; a cheap second channel later |
| Claude tool search | Deferred definitions, model searches, 3–5 tools load | Opus 4: 49%→74%, Opus 4.5: 79.5%→88.1%, ~85% fewer tokens, in large multi-server setups; "less beneficial" under 10 tools ([Anthropic](https://anthropic.com/engineering/advanced-tool-use)) | The client already does tool deferral; the server should not duplicate it |
| Code execution / Code Mode | Tools as a code API, browsed and scripted in a sandbox | 150K→2K tokens; 1.17M→~1K tokens for 2,500+ endpoints, vendor-reported ([Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp), [Cloudflare](https://blog.cloudflare.com/code-mode-mcp/)) | Ruled out by hard rule 1; the "search, then read at a chosen detail level" shape transfers |
| GitHub dynamic toolsets | Meta-tools to list and enable toolsets at runtime | Dropped from defaults; the winning move was cutting 101 tools to 52 by usage data, −53% tokens ([GitHub](https://github.com/github/github-mcp-server/discussions/1182)) | Fix the default set first; discovery meta-tools need proof they get used |
| RAG-MCP / MCP-Zero | Retrieve tools before selection | 13.6%→43.1% (RAG-MCP); 69%→95% on Claude-3.5 (MCP-Zero), but none on GPT-4.1 ([RAG-MCP](https://arxiv.org/abs/2505.03275), [MCP-Zero](https://arxiv.org/html/2506.01056v4)) | Helps at hundreds of tools; gains are model-dependent |
| OpenAI tool search and namespaces | Namespace description first, functions on demand; fewer than 10 per namespace | No accuracy numbers; changing the loaded set breaks cache ([OpenAI](https://developers.openai.com/api/docs/guides/tools-tool-search)) | Keep each chapter small |
| llms.txt | A well-known index file for models | 97% of files got zero requests in May 2026; Claude Code is among the few real readers ([Ahrefs](https://ahrefs.com/blog/llmstxt-study/)) | An index works when it sits on the page the agent already reads, not at a path it must discover |

Two lessons matter most for sky-brain. First, the **discovery step only pays when it is skipped rarely**, and nobody has measured how often models skip a `book`-style call and guess instead. MCP-Zero's gains came from a model that actively requested tools ([MCP-Zero](https://arxiv.org/html/2506.01056v4)). GitHub's runtime meta-tools left the defaults with no usage data published ([GitHub](https://github.com/github/github-mcp-server/discussions/1182)). The pointer to the book therefore has to live in the places a model already reads: tool descriptions, error messages and the server instructions. Second, **search over a handful of items adds a round-trip without adding recall**. The draft book has nine chapters and a contents page of about 600 tokens. At that size the model can simply read the contents, and `book_search` earns its place only once person pages or many recipes exist. Cloudflare adds that a search function "must be maintained and evaluated" ([Cloudflare](https://blog.cloudflare.com/code-mode-mcp/)).

## Only tools reach the model everywhere; instructions are unconfirmed in claude.ai

Sky-brain is used mainly from claude.ai and Claude Code, and these two clients behave differently. Claude Code documents that "only tool names and server instructions load at session start". It defers all MCP tools behind tool search by default, cuts instructions and upfront tool descriptions at 4,096 characters, and lets the model list and read resources itself ([Claude Code](https://code.claude.com/docs/en/mcp)). For claude.ai, Desktop and mobile, Anthropic's connector docs list tools, prompts and resources as supported, list resource subscriptions as unsupported, and **say nothing about server instructions** ([claude.com](https://claude.com/docs/connectors/building/index.md)). They also do not say whether the model can read a connector's resources on its own.

| Feature | Claude Code | claude.ai / Desktop | ChatGPT | Codex | Cursor | VS Code Copilot |
| --- | --- | --- | --- | --- | --- | --- |
| Server instructions reach model | Yes, cut at 4,096 chars | Undocumented | Used with tool metadata; first 512 chars | Yes; first 512 chars | Undocumented | Yes, since v1.104 |
| Prompts | User slash commands | "Supported", UI undocumented | Not documented | Not documented | "Supported" | Local harness only |
| Resources | User @-mention, and model can list/read | "Supported" | Not for model use | Not documented | "Supported" | Local harness only; Copilot sessions say return content in tool results |
| `readOnlyHint` | Parallel calls, safe retry | Required for directory listing | Honoured; writes need confirmation | `writes` mode prompts | Not mentioned | Affects confirmation, not a grant |
| `tools/list_changed` | Yes (interactive) | Undocumented | Manual Refresh | Undocumented | Undocumented | Editor client yes |

Sources: [Claude Code](https://code.claude.com/docs/en/mcp), [claude.com](https://claude.com/docs/connectors/building/index.md), [claude.com MCP](https://claude.com/docs/connectors/building/mcp.md), [ChatGPT developer mode](https://developers.openai.com/api/docs/guides/developer-mode.md), [OpenAI plugins](https://developers.openai.com/plugins/build/mcp-server), [Codex](https://learn.chatgpt.com/docs/extend/mcp?surface=cli), [Cursor](https://cursor.com/docs/context/mcp), [VS Code v1.104](https://github.com/microsoft/vscode-docs/blob/main/release-notes/v1_104.md), [VS Code MCP guide](https://github.com/microsoft/vscode-docs/blob/main/api/extension-guides/ai/mcp.md).

The design consequences follow directly. **Prompts are a user feature everywhere**, so "one prompt per recipe" helps a person start a recipe by name but never teaches a model anything on its own. **Resources are model-readable only in Claude Code.** VS Code's own guidance tells authors to "return content in a tool result when the agent needs it" ([VS Code](https://github.com/microsoft/vscode-docs/blob/main/api/extension-guides/ai/mcp.md)). **`list_changed` cannot carry a "reveal tools after reading the book" design**, because ChatGPT needs a manual Refresh and hosted Claude is undocumented. The tool list should stay static, as BOOK.md already proposes. Server instructions are worth writing, since they cost nothing and reach most clients. But they must be self-contained in the first 512 characters to satisfy OpenAI's advice, and every critical line in them must also appear in a tool description, because sky-brain's main client may drop them. Sky-brain's MCP server sets no `instructions` today (`apps/server/src/mcp/server.ts`). A canary test settles the claude.ai question in minutes: add an instruction such as "call `whoami` before any other sky-brain tool", then watch whether claude.ai does.

Compact mode also interacts badly with these clients. A `look`/`act` dispatcher hides each tool's argument schema behind a generic `args` object, which removes the definition-level guidance that keeps frontier schema errors near zero. It also collapses claude.ai's per-tool toggles ([Claude Help Center](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp.md)) and ChatGPT's per-tool write confirmation into one switch per dispatcher. Meanwhile, the clients that load everything up front are exactly where 18 tools is least likely to hurt a frontier model.

## Editable guidance is memory poisoning with more authority

Any text an MCP server places in a model's context is a prompt-injection channel. Tool descriptions are the most dangerous, because they load at connection time, before the user asks anything. Trail of Bits calls this "line jumping" ([Trail of Bits](https://blog.trailofbits.com/2025/04/21/jumping-the-line-how-mcp-servers-can-attack-you-before-you-ever-use-them/)). Approved text that later changes without re-approval is the rug pull. It was exploited in Cursor as **CVE-2025-54136**, and the fix was re-approval on any change ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-mcp-security-crisis-20260504/)). Human review alone fails when text can hide characters. The Rules File Backdoor hid instructions in Cursor and Copilot rule files with zero-width and bidi Unicode that stayed invisible even in PR review ([Pillar Security](https://pillar.security/blog/new-vulnerability-in-github-copilot-and-cursor-how-hackers-can-weaponize-code-agents)).

The model-proposed page is the sharpest risk in BOOK.md. It reproduces the loop behind several real attacks. In Windsurf, `create_memory` ran without approval, so an injection in a code comment became long-term memory that exfiltrated later conversations ([Embrace The Red](https://embracethered.com/blog/posts/2025/windsurf-spaiware-exploit-persistent-prompt-injection)). In MemoryGraft, **10 poisoned records out of 110 made up 47.9% of what was retrieved**, through combined keyword and embedding search ([MemoryGraft](https://arxiv.org/html/2512.16962)). A 2026 study got Claude Code to write a conditional rule into persistent memory from published content alone. The rule fired in later sessions with **81.7% average cross-session success**, and safety-reminder prompts barely reduced it once memory was poisoned ([arXiv 2609.13889](https://arxiv.org/pdf/2609.13889)). A book page is worse than an ordinary memory entry because the book is *meant* to be followed: one poisoned recipe steers every future session in the workspace. The proposing agent's token proves who sent the text, not where the words came from. An agent that read a hostile web page or a quarantined entry can propose in good faith.

BOOK.md already has the right backbone. Approval is required, proposals are never served before approval, pages are scanned, rate limits apply, and the five rules sit above every page. That matches the consensus fix of "suggest, don't save". The design is missing five concrete controls the evidence calls for. First, **approval bound to a content hash**, so any edit creates a new pending version; D32 superseding comes close and should be stated as the anti-rug-pull rule. Second, **rejection or visible rendering of invisible and bidi Unicode**, with the approval screen showing the exact bytes that will be served. Third, **structured proposals rather than free prose**: a recipe as up to 8 `{tool, note}` steps, notes short and free of URLs, emails, images and links. This follows OpenAI's advice to "eliminate freeform channels" ([OpenAI](https://developers.openai.com/api/docs/guides/agent-builder-safety)). Fourth, **provenance served with the text**: built-in text, person-written text and model-proposed text in distinct, labelled tiers, fenced as quoted data like the context packet (hard rule 7). Fifth, **never splicing person or model text into server instructions or tool descriptions**, the high-authority, connect-time slots ([OpenAI](https://developers.openai.com/api/docs/guides/agent-builder-safety)). Even with all five, residual risk stays real. Anthropic's best safeguards still let **1.4%** of attacks through on Opus 4.5 ([Anthropic](https://anthropic.com/research/prompt-injection-defenses)), and nobody has measured how often reviewers catch a subtly poisoned proposal.

## A paired benchmark of 30–40 tasks can settle the question in days

BOOK.md's benchmark (12 tasks, two models, with and without the book) has the right idea but is too small to detect the effects the literature predicts. Results vary from run to run: on τ-bench, Claude 3.5 Sonnet's retail score fell from 0.692 at pass^1 to 0.462 at pass^4 ([τ-bench](https://github.com/sierra-research/tau-bench)). With about 50 tasks and 3 trials, only differences of roughly 10 points are reliably detectable. That is the research notes' own estimate, and 12 tasks can only catch very large swings. The BOOK.md target of "at least 50% fewer 400s" also aims at the wrong error. Frontier models already make almost no schema errors ([MCP-Bench](https://arxiv.org/pdf/2508.20453)), so the signal lives in wrong-but-plausible tool choices, missing steps and wasted calls.

A credible minimal design follows Anthropic's eval loop ([Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents)) and τ-bench's state checks. Use 30–40 tasks drawn from real sky-brain use, with a held-out third that nobody tunes against. Mix single-call "which tool" tasks, multi-step board flows (next, claim, renew, report), look-alike traps (`search` against `list_memories`, a `search` right after `claim_task`), and refusal traps where the right answer is to ask or to say a tool does not exist ("approve these two goals", "delete that entry"). Grade by querying the PGlite test database after each run. Use an LLM judge only for free text, and spot-check it by hand, since LiveMCPBench found judges accept hallucinated completions ([LiveMCPBench](https://arxiv.org/html/2508.01780v2)). Run three arms with everything else held equal: A, today's tools; B, improved descriptions and instructions only; C, B plus the `book` tool. Optionally add D, compact mode, and an overload probe that adds 30–50 distractor tools from other servers. Run 3 trials per task per arm, on one frontier and one small model. Report task success (pass^1 and pass^3), first-call correctness, wrong-tool calls, extra calls over the minimal path, tokens including the book's own cost, and correct refusals, compared per task with McNemar's test or a paired bootstrap. Arm B against C is the decisive comparison, because it isolates the book from the cheaper description fix.

## Recommendation: build the bench now, ship a thin book after the window, defer the rest

**Now, during the measurement window (offline only).** Build `bench/book/` as above and run arm A to get a baseline, and measure how many tokens sky-brain's tool definitions take today. Nothing model-visible should change before the two-week memory-loop measurement ends. Server instructions or rewritten descriptions would change how models call `capture` and `search` and confound the result. BOOK.md's claim that "none of it changes the step 3 measurement" holds only for offline work.

**Right after the window (about 3–4 days, kept only if arm B or C wins on the held-out set).** Ship `defineTool` with the `book` metadata (chapter, use-when, pitfalls, related), and the test that every tool has a chapter. Render use-when and pitfalls into each tool's own description, because that is the one channel every client delivers. Add server instructions of at most 512 characters, built-in text only, and run the claude.ai canary test. Add **one** read-only tool, `book`, that returns the contents with no arguments and a chapter, tool or recipe given `id`. That covers `book` and `book_read` in a single tool and adds one tool instead of three. Chapter text comes from the code and the reviewed markdown files only. Point to the book from error messages ("see `book { id: 'errors' }`"). If arm B equals C, ship B only and keep the chapter text as the source for descriptions.

**Deferred, each with its trigger.**

| Deferred piece | Build it when |
| --- | --- |
| `book_search` | The book holds more than ~30 searchable items, or the eval shows models reading the wrong chapter |
| Person pages (notes, recipes, glossary) and the Book web page | The owner has written the same guidance into a chat, CLAUDE.md or a project file three or more times, or an eval failure cannot be fixed in code text |
| Model-proposed pages (`propose_book_page`) | Person pages are in real use, and the approval screen has hash-pinned versions, visible hidden-Unicode rendering and structured-only recipe input |
| Usage suggestions engine | The `tool_calls` log (counts only, no query text) has 30 days of data showing repeated error patterns |
| Compact mode (`look`/`act`) | Tool definitions exceed ~10K tokens or ~30 tools, or the overload probe shows wrong-tool errors in a client that loads everything up front |
| MCP resources and prompts | A user asks to start recipes by name, or SEP-2640 skills support is confirmed in claude.ai |
| Per-role and per-hat books | Scopes (D25 part 2) and hats (D30) ship |

## Conclusion

The brain book's real asset is its text, not its tools. The chapters already drafted under `docs/vision/book/` encode exactly the method knowledge the literature says moves accuracy. They do the most good inside tool descriptions and one cheap `book` call, not behind a search engine, a web editor and an approval pipeline. Every piece of extra machinery in the design either solves a scale problem sky-brain does not have yet (search, compact mode) or opens a poisoning channel (person and model pages) before anyone has shown the base text helps.

Building the benchmark first changes what the project learns. It turns "should we build the book" into a measurement, in the same spirit as the memory-loop measurement now running. It also gives sky-brain something the field lacks: a direct test of whether a separate usage guide beats good descriptions. If arm C does not beat arm B, the owner saves weeks of vision work and keeps the better descriptions. If it does, the triggers above say when each remaining piece has earned its place.

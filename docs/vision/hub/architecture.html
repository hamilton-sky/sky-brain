sky-brain architecture

How the brain is put together, what already runs in production, and the order to build the rest. It's a proposal, and nothing new here is decided yet.

sky-brain does not try to copy a human brain. It uses principles from human cognition to build a memory that is efficient, keeps evolving, and is shared by people and their AI agents.
built live at sky-brain.vercel.app partly built in the code, not exposed or not finished proposed design only
1 · System

One server, one database, many agents

Agents and people reach sky-brain over MCP or REST. Every request passes the Gatekeeper, which is plain server code. sky-brain never calls an LLM. The Stewards that look after memory run in your own connected model, as scheduled routines that pull their jobs like any other agent.

What runs today is the outer shell: sign-in, MCP, the board and most of the Gatekeeper. Memory has a table but no way in yet. That's the next job.

3 · Trust

Four levels of trust, and who may move an item up

This merges the second and third reviews. Agents may record what a test or a run proved, with the evidence attached, so you don't face a queue of trivial approvals. Only you can turn anything into a binding decision or rule. Repeating something doesn't raise it a level. Only independent sources count, traced through derived_from links.

4 · History

Two timelines: when it was true, and when we learned it

Append-only versions keep every change. Two dates per decision answer the question the reviews kept asking: why did we think otherwise a month ago? Real example from this project: hosting moved from Render to Vercel.

5 · Retrieval

From a task to a packet

Word search and vector search are fused with RRF, then the brain follows typed links: why something holds (derived_from), what it needs (depends_on), what replaced it (supersedes). The final ranking is where the cognitive signals go. Each one can be switched off and stays only if the benchmark shows it helps.

6 · The packet

What an agent receives with a task

The default size is small, about 4–5 summaries, each with a pointer to the full item. It's a default, not a cap. The agent can ask for a bigger budget, and the "what we don't know" lines tell it when to. This example is made up, for a task in this repo.

7 · Data model

8 · Build order

Nine steps, each one measured

This is BUILD-PLAN.md with the latest review's changes: the full loop comes before search tuning, there's a measuring step in the middle, and the benchmark includes a project the brain has never seen. Each step is in daily use before the next starts.

0

Benchmark

first
  • About 100 questions with known answers from sky-brain's history, plus tasks from Pathly, a project the brain hasn't seen.
  • Metrics: task success, correct retrieval, decisions kept, contradictions, tokens, latency. Three more from the review: approvals you had to give, stale or wrongly promoted items, and how often agents ask for more context.

Done when plain word search has baseline numbers.

1

Reliable memory

table exists
  • Extend entries and add entry_versions, links and episodes.
  • Add the trust levels and the Gatekeeper's rules for them, with an edit check so two agents can't overwrite each other.
  • Entries REST API and MCP tools: capture, search, get. Word search that works in Hebrew.

Done when tests prove that agents can't jump a trust level or edit in place, and that other workspaces can't read.

2

The full agent loop

proposed
  • claim_task returns the packet, including the "what we don't know" lines, which come cheap from data already stored.
  • report_task takes evidence. Lessons and observations are proposed, and question items can block a task.
  • A Digest page with Keep, Wrong and Undo.

Done when an agent coming back after a week answers "why" questions without reading the history.

3

Measure

gate
  • Run the benchmark three ways: plain retrieval, hierarchical memory, and sky-brain so far.

Done when sky-brain beats plain retrieval on decisions kept. If it doesn't, fix the loop before adding anything.

4

Hybrid search

proposedpgvector ready
  • pgvector 0.8.1 is enabled on the sky_brain Nanogres database (15 Nov), so halfvec(1024) and an HNSW index are available. Still to do: a multilingual embedding model, RRF, and typed, fan-damped hops.

Done when recall, precision and latency beat word search alone.

5

Cognitive signals, one at a time

proposed
  • Attention weight, then activation (needs the uses log), then the capture-context boost.
  • Each signal gets a run with it and a run without it.

Done when each signal shows a gain, or is switched off.

6

Consolidator

proposed
  • One Steward, run as a scheduled routine in your model. It merges duplicates, writes the Digest, schedules "still true?" checks and produces a weekly contradiction report.
  • It only proposes, and it counts sources by lineage.

Done when a month of nightly runs adds no contradictions.

7

Growth and export

proposed
  • Layered summaries, retention by tier, hard forget through summaries and embeddings, cold archive, the md vault and a git export.
8

Beyond code

later
  • Domain packs with versioned types, sharing per project, imports, files, and other audiences.
